# Otogura — 音蔵

**[日本語版はこちら / Japanese version](README.md)** — it also carries the full release history.

A music player for Windows, built on Electron.
Narrow your library down with three columns — Genre → Artist → Album — and play from the list below.

**A storehouse for sound.** As the name says, **it was built for large libraries.**
It is measured and corrected against the author's own **171,085 files / 387 GB**.

**This app is a worked example of letting an AI build something.** How it was made is at the bottom.

### Running from source

#### 1. Set up

You need [Node.js](https://nodejs.org/) (18 or newer).

```
git clone https://github.com/xmichinokux/otogura.git
cd otogura
npm install
```

#### 2. Put an icon on the desktop (recommended)

Double-click **`デスクトップにアイコンを作る.bat`** once ("make a desktop icon").

An Otogura icon appears on your desktop.
**Launched from that icon, no console window flashes up at all.**

<img src="icon.png" width="72" alt="icon">

To keep it in the Start menu, right-click the new icon → "Pin to Start".

The icon artwork is generated by `tools/make-icon.js`.
There is no image file checked in — it is kept in a **re-generatable** form
(to change the colours or shape, edit that and run `node tools/make-icon.js`).

#### 2'. Starting without making an icon

Double-clicking **`起動.bat`** ("launch") also works — a console window flashes briefly.

From a command line:

```
npm start
```

All of these do the same thing underneath: they call `electron.exe` directly.
Going through `npm start` puts one more window in between, and
**closing that window takes the app down with it.**

## Adding your music

Use **"Add a folder"** at the bottom of the window and pick a folder with music in it.

It picks up **`.mp3` `.m4a` `.wav` `.flac`**.
Some CD rippers write `.m4a` even when you asked for MP3
(the author's did — see `拾う拡張子` in `src/library.js`).

**aiff and m4p are not picked up.** They did not play when tested
(m4p is DRM-protected iTunes audio). **Only formats confirmed to play** are listed.

**wav files rarely carry tags** — of 1,268 on hand, only 44 had any.
Adding them makes the "untagged" pile jump, but the default "Hide untagged" keeps them out of sight.

**Songs over 100 MB are not measured for loudness.**
Measuring loads the whole file into memory, which does not hold for large wavs
(measured: a 1,095 MB wav peaked at about 2.1 GB and took 18 seconds).
Only the measurement is skipped — **they still play**, and the status bar says so.

**ALAC (Apple Lossless) inside `.m4a` will not play.**
Chromium does not support it (observed: `DEMUXER_ERROR_NO_SUPPORTED_STREAMS`).

**They are not dropped from the list.** They stay, and the reason is shown when you click one.
Having songs you own quietly disappear is worse.
Auto-advance and ⏭ skip them, but **the number skipped is shown on screen**.

Settings and scan results are stored here (**your music files are never moved**):

```
C:\Users\<you>\AppData\Roaming\Otogura\
  settings.json         folders, playlists, volume, and so on
  library-cache.json    remembered tags (makes every scan after the first one fast)
```

This folder name is derived from the app name (an Electron rule).
Renaming the app changes where things are stored, so **anything under an older name is carried over on first run**.
It is copied, not moved — the old folder stays where it was.

## What it does

| | |
|---|---|
| Filtering | Three columns. **Tabs switch between "Genre / Artist / Album", "Date (Year / Month / Day)" and "🌐 Resonance"**. Ctrl / Shift select more than one |
| Playing | **One click** on a row. **▶ alone also starts playback** — you do not have to pick a song first |
| Shuffle | **Never two songs by the same artist or album in a row.** **Songs you have played least are favoured**, so forgotten ones surface. It draws from **what is in the list below**. Individual songs can be **kept out of the draw** |
| Volume | A master volume slider **plus loudness evening-out between songs** (the same idea as ReplayGain) |
| Sorting | Click a heading for title, artist, album, **date** or play count. Column widths are adjustable |
| Default order | **By artist** (within one artist: album, then track number) |
| Playlists | Create, reorder, export and import m3u |
| Editing tags | Genre, artist and album can be corrected (**MP3 only**) |
| Untagged songs | **Hide / show** toggle, so raw exports stay out of the way |
| Following a word | **Optional.** Enter one word and it looks for music that word leads to, then tells you what you already own (needs an API key) |
| Entering an API key | **Optional, off by default.** With one entered, you can write how you feel and have the AI build a set |
| Removing from the list | Removable, and **restorable**. When something is removed, "↩ Put back N removed songs" appears |

### No two in a row by the same artist or album

Shuffle **avoids the artist (and album) of the song that just played.**

**Where this actually matters was measured before it was added.** 3,000 draws; the figure is how often a draw repeated the previous one.

| Range | Same artist | Same album |
|---|---|---|
| Everything, 86,044 songs | 0.1% → 0.0% | 0.0% → 0.0% |
| One genre, 6,048 songs | 1.5% → 0.0% | 0.7% → 0.0% |
| 10 albums, 101 songs | 9.3% → 0.2% | 9.3% → 0.2% |
| **5 albums, 54 songs** | **28.1% → 4.7%** | 19.9% → 1.4% |
| **3 albums, 35 songs** | **32.5% → 1.6%** | 32.5% → 1.6% |
| **3 artists, 180 songs** | **36.5% → 0.9%** | 12.2% → 0.2% |

**Across a wide range it was never happening in the first place.** It earns its keep once you have narrowed to a handful of albums.

**Only the single previous song is considered.** The wider that window gets, the less it is a draw at all,
so this stops at the weakest useful form of "no repeats".

**When it cannot be avoided, it is not avoided.** Select one album and every candidate is the same
artist and the same album. Refusing there would mean not playing what you chose.
It relaxes in stages: a different artist → at least a different album → no constraint.

**Nothing is locked out.** The measurements above confirm that in every range, **every song can still come up.**

### Building a set (optional, off by default)

Enter an API key with **"🔑 Enter an API key"** at the bottom, and a bar appears above the three columns.

```
🎧 [How are you feeling?]  [Build a set]     🌱 [Enter one word to trace]  [Trace]
Narrow [──●──] Wide   10 songs [──●──] 80 songs   Classic [──●──] Off-centre   [🌀 Wide reading: off]
```

**There are two ways in,** and which one you get is decided before you press anything.

| Way in | What happens |
|---|---|
| 🎧 **From a mood** | Narrows to the genres that fit what you wrote, then **builds a set** from them |
| 🌱 **Following a word** | Looks for music that word leads to and **gathers what you own into the "🌐 Resonance" tab** |

**Only 🎧 builds a set.** 🌱 stops at narrowing; after that you play with ▶ or 🔀
(what the trace found simply becomes the range you are listening to).

#### The sliders — how wide to look, and how much to pick

There is **one set of sliders**, and it **applies to both ways in**.
The two paths end at the same place, so the meaning carries over.

| Slider | What changes |
|---|---|
| **How wide** | Candidate songs handed to the AI (both) ／ names followed (🌱) ／ genres offered (🎧) |
| **How many** | Songs in the set (🎧 only — 🌱 does not build a set, so it has no effect) |
| **Classic ↔ off-centre** | Whether to stay with the classics of that mood or step away from them. Stepping away makes the model think harder, so it costs a little more |
| **🌀 Wide reading** | An independent on/off switch. Later in a set it jumps to distant contexts; what it picks once it lands is decided by the strength slider |

| Notch | Candidates | Names followed | Genres | Songs | 🎧 cost | 🌱 cost |
|---|---|---|---|---|---|---|
| 1 narrow | 50 | 10 | up to 2 | 10 | ~¥3.5 | ~¥6 |
| 2 | 100 | 20 | up to 3 | 20 | ~¥6 | ~¥8 |
| **3 usual** | **200** | **35** | **up to 5** | **30** | **~¥8.3** | **~¥10** |
| 4 | 400 | 55 | up to 8 | 50 | ~¥12 | ~¥13 |
| 5 wide | 800 | 90 | up to 12 | 80 | ~¥24 | ~¥18 |

🌱 became more expensive in 0.18.0. **To surface more bands**, the artists shown to the model went
from 150 to 800 and the names followed from 21 to 35. (It still does not build a set, so it is one round trip.)
"Candidates" and "songs" apply to 🎧 only.

**The middle notch is what it always used to do.** Leave the sliders alone and nothing changes.

**The top was capped at 800 songs because of diminishing returns, not cost.**
More candidates does not mean a better set — the model simply has more to survey,
and considers each song less carefully.

**Narrow width with a high song count runs out of candidates.**
(You cannot take 80 songs from 50.) It then cuts down to what is available and
**says on screen that it did.** It will not quietly hand you a short set.

The costs are **rough guides.** They shift a little with the length of song and artist names,
and both pricing and exchange rates move (Opus 5 at $5 / $25 per million tokens, converted at ¥150/$).

**A finished set does not start playing by itself.** You get a playlist. Press ▶ when you want to hear it.

### The AI does not choose songs. It chooses a filter

```
what you wrote
   ↓
the three columns move to that state → the list below narrows → a set is built from there
```

There are three reasons for this. **You can see what it did** — and if you disagree, just correct it by hand.
**It cannot invent songs you do not have** — every name that comes back is checked against your library.
And **from there on, the ordinary shuffle still works.**

#### Candidates: fewer artists, several songs each

The AI is handed 200 candidate songs. **How those 200 are chosen matters.**

Draw song by song and bands you own more of get picked repeatedly.
The AI then chooses from a lopsided 200, and even with "do not repeat an artist" in the prompt,
**the same band lands every other slot while technically obeying the rule.**

So it goes round the artists taking one song each, and starts another lap when it needs more.
When several songs come from one artist, it walks their albums one at a time.

**Since 0.34.0 it deliberately narrows the artists and hands over several songs each**
(2–4 depending on the slider — at the usual notch, 67 artists × 3 songs rather than 200 × 1).
With one song per artist, **the AI cannot choose which song to play** — it only gets a random
track from each discography. Which song is a band's signature is exactly what the AI knows,
so that choice is handed to it. There are still at least twice as many artists as songs in the set.

| Situation | Most songs from one artist (before → now) |
|---|---|
| Everything, 85,327 songs | 2.2 → **1.0** |
| Hardcore, 12,537 songs | 4.4 → **1.0** |
| 30 artists, 5,263 songs | 17.8 → **7.0** |
| 5 artists, 1,667 songs | 53.4 → **40.0** |

**In narrow ranges it is already at the floor.** With only five artists, 200 songs must repeat.
**When it cannot be avoided, it is not avoided** — the same principle as shuffle.

**Since 0.34.0 this draw is separate from shuffle.** Shuffle weights songs you have played least,
to dig up what you have forgotten. Building a set wants the opposite — a band's core songs —
so play counts are not consulted here at all.

Within an artist, the draw favours where hit songs tend to sit on an album. Measured across
6,743 albums with complete track numbering, the share of intro/outro/interlude titles is
6.78% at track 1 (10.5× the baseline), **0.31% at track 2** (the cleanest spot on the record),
0.89% mid-album, and 2.04% on the closer (3.1×) — which matches how records are actually made.
A song also gains weight if the same title appears on two or more of that artist's albums
(your own library voting for it) or if it sits on a best-of or discography release.

**The last pick from each artist drops the weighting entirely — that one is the spice.**

Once a set is built, **the number of repeated artists is shown on screen.** Passing over it in silence
just looks like the problem was never fixed.

### The finished set

```
🤖 a set the AI named (30 songs)  ← it stays as a playlist
   ↓
▶ plays it from the top. Each song carries a note on why it sits where it does
```

```
Artist — Album　🤖 why this song, in this position
```

**It stays as a playlist.** Keep it if you like it; reorder it by hand, delete it, or export it as m3u.

**A built set plays in the order it was built.** Shuffle turns itself off.

### The 🌐 Resonance tab

Trace a word and a "🌐 Resonance" tab is added to the three columns.

| Column | What is in it |
|---|---|
| Word followed | which word led here |
| Artist | artists you turned out to own |
| Album | their albums |

It behaves like the other columns — **Ctrl / Shift select more than one**, and you can type to search.
While this tab is open, **only songs the trace found** appear below.

The words you followed can be **renamed or deleted** afterwards.
That row appears **only while the "🌐 Resonance" tab is open** — on the other tabs there is nothing to press it for.

```
🌐 3 matches・120 songs   [word followed (21)] [✎] [×]   [× Clear all]
```

There is deliberately **no "build a set" button here. Things laid out to be pressed get pressed**
(in practice the author ended up making the same thing several times over).
Sets are built in one place only: the bar at the top.

Up to 0.15.1 **the button was removed but the same behaviour was still inside "Trace"** —
tracing quietly built a set as well. Now tracing only traces.

### Worth checking (names not found in your library)

```
🌐 3 matches・120 songs   [word followed (21)] [✎] [×]   [▶ Worth checking 12]   [× Clear all]
```

Click to open. **Matches (songs you can actually play) are the point; this is a sidelight,** so it starts folded.

#### Matching is deliberately stricter on one side than the other

| | Matched against | Why |
|---|---|---|
| **Matches** (things it will play) | Exact artist only. **Strict** | Playing the wrong song is the worse outcome |
| **Worth checking** (things it calls missing) | Partial match on artist, album and song titles. **Loose** | Sending you out to buy something you already own is the worst outcome |

Invert the same test naively and **everything you only hold as an album title, a song title,
or a track on a compilation turns into "you do not have it".**

Measured across 86,044 songs (three quarters of the names are held in some form):

```
 22 names … strict: 15 "missing" → loose: 5 (10 were owned)
150 names … strict: 110 "missing" → loose: 37
```

**When it errs, it errs towards "you own it".** Short names get absorbed into album and song titles
and fall on the "owned" side; that was a deliberate call.
Missing something you do not own is better than sending you to buy something you already have.

#### It is not offered as a shopping list

Names that were not found are **three different things mixed together, and they look identical.**

| | |
|---|---|
| ① | genuinely not owned |
| ② | owned, but spelled differently |
| ③ | the AI produced something that does not exist |

Hence "worth checking". **There is no buy-it or download-it mechanism.**

#### Depth changes the meaning

| Depth | Meaning |
|---|---|
| 1 | you have no way in (an unexpected gap) |
| 3 or more | not reached yet (the far edge) |

Ordered the same way as matches: **heaviest first** (deeper and newer float up).

**Nothing was missing from the JSON.** name / depth / description, plus keyword / savedAt per tree,
are enough. No change is needed on the Resonance side.

Clearing only removes the trace records. **Your music files are never touched.**

### Importing a fixed JSON shape

Otogura can read the shape below, so traced trees can be brought in from outside.
**The entry point is not exposed in the public build** — since 0.10.0 you can trace from inside the app,
so it is not needed. The shape and the handling are still there if it ever is.

```json
{
  "version": 1,
  "exportedAt": "2026-08-29T01:57:44.435Z",
  "entries": [
    {
      "keyword": "the word followed",
      "savedAt": "2026-08-29T01:56:16.575Z",
      "nodes": [
        { "name": "artist name", "genre": "music", "description": "why they connect", "depth": 3 }
      ]
    }
  ]
}
```

The author's other app, **Resonance in Kokoro OS**, exports this shape
(Resonance is not yet public; you do not need it — "following a word" above does the same thing).

### `name` is matched against artist only — decided by measurement

What should a tree node's name be matched against? Counted on the real thing
(7 trees, 147 nodes) against a library of 86,044 songs.

| Matched against | music nodes that hit |
|---|---:|
| **artist only** | **22** |
| artist + album | 22 (**album adds nothing**) |
| all three | 22 (**title adds nothing**) |

Adding `title` gains 13 hits overall, but every one of them was **a coincidental name collision outside music**:

```
the name of a philosophy  [other] as a song title,  2 songs
the name of an artist     [art]   as a song title,  1 song
the name of a place       [place] as a song title,  1 song
the title of a film       [movie] as a song title,  5 songs
the title of a film       [movie] as an album,     10 songs
```

Song titles are often short ordinary words, and **they collide with unrelated things by accident**.
A hit like that means nothing. Only nodes whose `genre` is `music` are used.

### How weighting works

**Deeper is stronger, newer is stronger.**

- Depth 0–3 scales 1× to 4× (a hit somewhere distant is the more interesting discovery)
- Recency decays gently, halving over 60 days (a hard cut-off would kill older trees outright)
- If the same name appears in two trees, **the heavier one's reasoning is kept**

### Speed and where it lives

Matching is **a single pass over 86,044 songs** (measured at 25 ms).
Searching every song per name would be 22× the work, so the songs are walked once instead.

```
C:\Users\<you>\AppData\Roaming\Otogura\resonance.json
```

Traced trees and imported trees **accumulate in the same place**. "× Clear all" removes them.
**Only that record is removed.**

## The one place this app talks to the outside

Otogura otherwise **runs entirely on your machine.** This feature is the single exception.

| | |
|---|---|
| **Sent** | the list of genre names (with counts) ／ the list of years acquired ／ what you typed ／ **the title, artist and album of 200 candidate songs** |
| **Not sent** | **file paths, and the audio itself** (since 0.8.0 the titles of the 200 candidates are sent) |
| **When** | only when you press the button. Nothing goes out in the background |
| **Default** | **off.** Until a key is entered, the input bar does not even appear |
| **Model** | `claude-opus-5` |

**Handing over every song is not possible.** Counted on the author's library,
**86,044 songs ≈ 2.1 million tokens** — past the million-token context limit.
What is actually sent is **the genre list alone, about 725 tokens.**

### Where the key lives

**The renderer never touches the key.** Only the main process holds it.

It is stored in this one file, **encrypted with Windows DPAPI**:

```
C:\Users\<you>\AppData\Roaming\Otogura\ai-key.bin
```

**It is never stored in plain text.** Where encryption is unavailable, storing it is refused outright.
There is **no way to read the key back** from inside the app — a screen that can read it is a screen it can be stolen from.
To remove it, press "🔑 Delete the API key" (the same button). Only the key file is deleted.

Keys are made at [console.anthropic.com](https://console.anthropic.com).
For the genre list alone, a run costs **under one yen**.

### The three-column tabs

The tabs above the columns change what you filter by.

| Tab | What the columns hold |
|---|---|
| Genre / Artist / Album | as before |
| **Date (Year / Month / Day)** | filter by when you acquired it |
| **🌐 Resonance** | what a traced word turned up |
| **Genre (grouped)** | scattered genre names gathered into a browsable size |

**Switching tabs keeps the previous tab's filter.**
Pick a genre, then a year on the date tab, and you get **the intersection**.
Both tabs take Ctrl / Shift for multiple selection.

Because filters persist, **a filter can be in effect where you cannot see it.**
So hidden tabs show their count, like `● 3`.

Date columns sort **newest first**. On the author's machine the granularity came out like this:

| | Buckets | Largest bucket | Median |
|---|---:|---:|---:|
| Year | 24 | 15,397 songs | 1,079 |
| Month | 222 | 11,559 songs | 113 |
| Day | 1,691 | 6,758 songs | 12 |

The largest "day" bucket (6,758 songs on 2014-09-12) is **a bulk import day**.
It lets you find things by "the batch I added back then".

Songs with no known date do not appear while a date filter is on. Set the date tab to "All" to get them back.

### Filters take multiple selections

**Ctrl- or Shift-click** in the three columns to select more than one.

| Click | Result |
|---|---|
| plain click | just that one |
| **Ctrl+click** | add one at a time. **Click again to remove it** |
| **Shift+click** | the range from the last one clicked |
| "All" | clear that column's selection |

Once something is selected, the count appears to the right of "All (N)".

Re-selecting in a column above clears the selections below it.
An **impossible combination** — three genres plus an artist in none of them — would otherwise linger,
and there would be no way to tell why you were looking at zero results.

### Songs you do not want in the shuffle

"Out of the draw" on a row means that song **stops being drawn by shuffle.**

**This is not the same as removing it from the list.**

| | In the list | Plays when clicked | Drawn by shuffle |
|---|---|---|---|
| an ordinary song | yes | yes | yes |
| **out of the draw** | yes (with a faint 🚫) | yes | **no** |
| removed from the list | no | no | no |

**Stepping through in order (⏭ or auto-advance) still plays them.** Only the draw is affected.
This is for songs you do not want **arriving unannounced**, not for songs you never want to hear.

You can also select several and take them out or put them back in one go from the tool row below.
The setting is remembered, so it survives closing the app.

### What "Date" means

The "Date" column is **the file's modification time**. Click it and it sorts **newest first**.

**Creation time is not used.** It was measured and found useless (2026-08-29, 400 samples in two locations).

| | Spread | Usable |
|---|---|---|
| creation time | all 400 under `E:\iTunes Music` sit in **2026-08** | ✗ overwritten on the day the disk was copied |
| **modification time** | **112 distinct months** (2014-09 / 2015-07 / 2017-04 …) | ○ survives copying and tracks when you got it |
| the year in the tag | 106 of 400 are **empty to begin with** | ✗ that is the release year, not when you got it |

On the author's machine (1,630 songs under `Documents\MP3`) it spreads out like this:

```
2008 ██ 39      2016 ██ 33      2022 █ 18
2009 ███ 54     2017 ██ 24      2025 █████████████ 245
2010 █ 7        2018 ██ 26      2026 █████████████████████ 1058
2013 ██ 29      2019 ████ 67
```

**Editing tags does not move the date.** It is captured before the write and restored afterwards.
Otherwise the songs whose genre you just corrected would all sort to the top as "newest".

Songs with no known date show "—" and sink to the bottom when sorting newest first.

This costs no extra reading. The cache comparison already looks at the file's metadata, so the date **just comes from there**.

### Shuffle draws from whatever is currently filtered

Pick an artist or album in the three columns and **shuffle stays inside it.**
Change the selection and **the pool changes without stopping playback.** With nothing selected, everything is in play.

It used to remember "the list as it was when you pressed play", so that changing a filter mid-song
would not change what came next. But **getting back to whole-library shuffle then required stopping first**,
and the author asked for it to be rebuilt (2026-08-29).

The list only draws 2,000 rows, but **the pool is not cut there.**
What is in play is "the currently filtered range", not "the 2,000 rows you can see".

---

### Files are never deleted

"Remove" on a row **only removes it from the list** — the file itself stays.
This codebase does not contain **a single line** that deletes a file.

The one exception is tag editing, which does rewrite files.
Even then, **tags other than the fields you supplied are left alone** (it uses `node-id3`'s `update`,
never `write`). That the audio data is unchanged is verified by `check-tags.js`.

**Only MP3 tags can be rewritten,** because `node-id3` handles ID3 tags only.
Pick an `.m4a` and it says so before writing, and skips it (**reading and playback still work**).

## About large libraries

Measured and corrected against the author's library — **171,085 files / 387 GB**.

| | Before | After |
|---|---|---|
| Artwork | held for every song (**17.8 GB** — this is what was crashing it) | only the song being played |
| Second scan onwards | everything re-read every time | **only files that changed** |
| Closing mid-scan | that run's work **thrown away entirely** | **saved every 30 seconds; resumes** |

### Tag-reading speed (read these numbers carefully)

| | Per song | For 171,085 songs |
|---|---|---|
| a file touched for the first time | **~36 ms** | **~100 minutes** |
| a file read before | ~1 ms | ~3 minutes |

**Do not mix these two up.** The author did, once.
Measuring the same sample twice in a row, it read as "changing a setting made it 24× faster".
In fact **the OS had simply cached the files** — the setting had nothing to do with it.
When comparing speeds, measure **files that are new to the machine both times**.

Concurrency (8 / 16 / 32 / 64 / 128 at once) was measured too, and **made no difference**.
The disk is what you are waiting on; more parallelism does not help.

### Half of them were not songs

Counting the author's library: **of 171,092 entries, 85,039 were not songs.**

Copying from macOS to a Windows-style disk leaves a small companion file next to each real one
(the ones starting `._`). There is no audio in them.

- scanning took **twice** as long (103 minutes → **52 minutes**)
- the list was so full of them it was unusable

**Until they were counted, it just looked like "a lot of songs".**
Anything starting `._` is now skipped. The real count was **86,057**.

### Not making you wait

The first scan takes a while. But:

- **the previous list appears immediately** (from the cache — zero wait)
- re-reading happens **in the background**, and songs join the list as they are found
- progress and **an estimate of the time left** show at the bottom
- **close mid-scan and it resumes** next time you open it
- **you can stop it** (see below)

### If it bogs the machine down, you can stop it

Scanning a large library **occupies the disk for a long stretch**
(about 50 minutes for the author's 86,000 songs). It is the disk, not the CPU, that saturates,
so other applications' reads and writes slow down too.

While scanning, "Rescan" becomes **"■ Stop"**. Press it and it wraps up where it is.

**Stopping costs you nothing.** What was read is kept, what has not been looked at yet is filled in
from the previous record, so **the list does not shrink** — nor does the cache.
**Next time, it picks up from there.**

**It can be stopped during the counting phase too.** On a large library, counting alone takes
297 seconds (measured), and if stopping only worked once reading had begun, that whole stretch would be uninterruptible.

Closing the window also stops it. The scan runs inside the app —
**there is no second process and nothing left resident.** Close it and the process ends with it.

The list draws at most 2,000 rows at a time (narrow with the three columns above for more).
The number omitted is shown on screen.

That 2,000 was **measured, not guessed** (500 rows = 39 ms / 2,000 = 146 ms / 85,000 = 5,915 ms).
It was first set to 500 without measuring, and that was not enough even after filtering.

## Verifying that it works

The logic can be checked without opening the window.

```
npm run test-music     # generate silent MP3s to test against
npm run check          # run all 18 checks below
```

| Check | What it watches |
|---|---|
| `check-shuffle.js` | whether shuffle surfaces songs you have forgotten |
| `check-loudness.js` | the loudness-evening calculation |
| `check-playlist.js` | saving, cleaning and m3u handling of playlists |
| `check-url.js` | playback with awkward characters in the path |
| `check-tags.js` | that writing tags **leaves the audio data unchanged** |
| `check-cache.js` | **a forgotten import, a `catch` that swallows, the renderer↔main wiring, carrying data over after a rename** |
| `check-stop.js` | that stopping a scan — **or a missing folder** — never shrinks the list or the cache |
| `check-sort.js` | ordering (a synthetic fixture **plus the author's whole real library**) |
| `check-ai.js` | the prompts sent to the AI, and **checking what comes back against the library** |
| `check-resonance.js` | reading resonance trees and matching them to songs |
| `check-knob.js` | **that the sliders reach both paths, and that it never asks for more songs than it has candidates** |
| `check-genre.js` | grouping scattered genre names |
| `check-own.js` | keeping your own recordings out of shuffle and out of the AI |
| `check-naoshi.js` | the correction layer (`手直し.json`) — that hand edits win over it |
| `check-hist.js` | the history of what you typed, and clearing it |
| `check-lang.js` | **that every string shown has an English translation, that the prompts really are English, and that no two scripts declare the same global** |
| `check-en.js` | **opens the real window in English and reads it** (works with Otogura still running) |
| `check-ui.js` | opens the real window and reads it (**close Otogura before running this one**) |

`check-cache.js` grew out of bugs that actually happened. All of them are **invisible until you run the thing**:

| What went wrong | How it looked |
|---|---|
| one import line missing, and a `catch` swallowing it | correct right after fixing, but **back to the old state when reopened** |
| the screen offered "you can restore them" for an action that **existed nowhere** | a removed song never came back, and **re-adding it did not bring it back either** |

The second one had an entry in `preload` and a handler in main — **and nothing in the renderer calling it.**
So the check looks **both ways**: does everything the renderer calls exist on the other side,
and **is everything the other side offers actually called?**

To measure scan speed against your own library:

```
node check-scan.js "D:/Music"
```

## How it was made

**The person who specified this app did not write a single line of its code.**

1. In **[Kokoro OS](https://kokoro-os-v2.vercel.app)'s Baton**, they wrote what they wanted to build
   and answered its questions about "things not yet decided", producing a **specification**
2. That specification was handed to **Claude Code** to implement
3. Bugs found in real use were fixed as they came up

**What the specification failed to ask about** also became clear.

| Gap | What happened |
|---|---|
| how to start playback | you could not tell where to click, and could not play anything for a while |
| what happens when a song ends | next, repeat and shuffle were missing entirely |
| **how many songs** | tested happily with 4, the layout broke at 1,000, and it crashed at 170,000 |
| **how to undo hiding** | only "hide" was built — **there was no way to unhide** (only text saying there was) |

On the strength of that, Baton now asks about **operation** (how it starts and how it ends)
and **volume** (how many of them there will be).

The code carries, in Japanese, **why it was written that way** and **what was got wrong**.
Notes marked `★` are records of mistakes actually made.
